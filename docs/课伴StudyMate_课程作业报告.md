# 课伴 StudyMate：构建一个能说会做的课业协作智能体

## 一、项目简介与需求描述

小组作业通常需要拆分任务、确定负责人、安排时间并持续更新进度。如果这些信息只保留在群聊里，就容易出现“谁负责哪一项”“什么时候有空”“这项任务是否已经完成”等信息不一致的问题。

我们围绕这一场景开发了“课伴 StudyMate”。用户用自然语言描述作业要求，智能体结合项目成员生成可检查的任务草案；用户确认后，系统把任务写入数据库，再根据成员明确填写的可用时间安排日程。后续可以查询、开始、暂停、继续或完成任务，并导出当前项目计划。

课伴也支持一般知识问答、联网资料搜索和城市天气查询。课业协作是主要业务，查询辅助功能用于展示智能体对不同外部工具的选择和调用能力。

### 1.1 主要需求

| 需求 | 对应功能 |
| --- | --- |
| 根据作业要求明确分工 | 自然语言拆解、负责人和估时草案、确认后保存 |
| 根据实际时间制定安排 | 成员可用时间、日程草案、冲突及工时覆盖检查 |
| 在多轮对话中继续操作 | 会话历史、当前任务焦点、待确认草案持久化 |
| 记录实际进度 | 待开始、进行中、已暂停、已完成四种任务状态 |
| 同时参与不同小组 | 新建与切换项目，分别保存成员、任务、日程和对话 |
| 区分当前发言者 | 选择聊天成员，按项目和成员恢复历史 |
| 便捷输入与查看成果 | 语音转文字、回复朗读、网页看板、Markdown 导出 |
| 获取外部资料 | Tavily 网页搜索、Open-Meteo 天气查询及来源展示 |

当前的成员切换是本机视角选择，不是手机号或微信登录，也不等于个人账号权限隔离。多项目分别保存数据，但暂不自动检查同一个人跨项目的日程冲突。

## 二、业务流描述

### 2.1 课业任务主流程

```text
新建或选择项目，选择当前聊天成员
    ↓
输入作业要求、截止时间和分工需求
    ↓
模型理解意图，读取实际成员信息，生成任务草案
    ↓
用户检查并确认采用
    ↓
通过 MCP 工具把正式任务写入 SQLite
    ↓
填写成员可用时间，生成并校验日程草案
    ↓
用户确认保存，查看项目日程
    ↓
多轮对话或卡片操作：开始 → 暂停 → 继续 → 完成
    ↓
调用导出工具，下载当前项目计划
```

草案与正式任务分开保存，生成草案不代表任务已经落库。排程存在冲突或容量不足时，系统说明缺口，不捏造空闲时间，也不把不可行排程保存为正式日程。暂停任务保留内容和截止时间，不自动顺延。

### 2.2 外部信息查询流程

普通知识问题由模型直接回答；需要公开资料或最新信息时，模型可以调用 `web_search`，根据实际返回的摘要回答并展示来源。城市天气问题优先调用 `get_weather`：先识别城市、查询经纬度，再请求结构化天气数据。城市不明确时需要澄清，同名地点需要确认。

查询天气或网页不会自动改写课业任务。用户需要据此规划任务时，应在后续消息中明确提出，系统继续按草案确认流程处理。

## 三、实现说明

### 3.1 系统结构

```text
网页：HTML / CSS / JavaScript
    │ 自然语言、按钮操作、语音转写
    ▼
FastAPI 后端与 Agent 编排
    ├─ 千问 qwen-plus：理解问题、选择工具、组织回复
    ├─ 会话管理：项目、成员、历史、焦点及草案
    └─ MCP 客户端（stdio）
           ▼
       独立 MCP 工具服务
           ├─ SQLite：成员、任务、可用时间、日程与导出记录
           ├─ Tavily API：公开网页搜索
           └─ Open-Meteo API：城市地理编码及天气数据
```

| 层次 | 技术与作用 |
| --- | --- |
| 模型 | qwen-plus，通过兼容接口进行自然语言对话及 Function Calling |
| 工具协议 | 官方 MCP Python SDK，客户端与独立工具进程通过 stdio 通信 |
| 服务端 | Python 3.11+、FastAPI、httpx |
| 数据存储 | SQLite，保存业务数据、会话与防重复记录 |
| 前端 | 原生 HTML、CSS、JavaScript；本地 Markdown 渲染与清理 |
| 语音 | 浏览器 Web Speech 语音识别及语音合成 |
| 外部接口 | Tavily Search API、Open-Meteo Geocoding / Forecast API |

老师推荐使用 MCP 或兼容框架，本项目采用了真实 MCP 服务。系统并非只在聊天中输出一份计划：工具执行会改变实际数据库，网页和下载文件反映这些真实变化。

### 3.2 模型如何调用工具

后端读取当前项目和成员会话，将实际 MCP 工具定义提供给模型。模型返回工具名和参数，应用校验参数、注入可信项目范围及防重复标识，再通过 MCP 执行。工具返回成功或失败结果后，模型继续组织回答。

目前注册了13个 MCP 工具：

| 类型 | 工具 |
| --- | --- |
| 成员管理 | `manage_member` |
| 任务管理 | `list_tasks`、`create_tasks`、`update_task` |
| 可用时间 | `get_preferences`、`set_preferences` |
| 日程 | `check_schedule`、`propose_schedule`、`save_schedule` |
| 项目与文件 | `get_plan`、`export_plan` |
| 外部信息 | `web_search`、`get_weather` |

`draft_tasks` 和 `draft_schedule` 是 Agent 层的本地编排工具，不计入上述13个独立 MCP 工具。它们先形成待确认草案，最终写入通过真实 MCP 工具完成。

网页显示实际处理阶段、工具执行与等待时间；这些是执行进度，不是模型内部思考过程，也不是虚构的进度百分比。按钮操作复用相同工具链，不需要每次都额外请求模型。

### 3.3 数据持久化与多轮记忆

SQLite 保存项目、成员、任务、可用时间、日程、会话、请求及导出快照。会话绑定项目和成员，保存完整对话回合、待确认草案和任务焦点。用户先指定任务，再说“暂停它”“继续它”时，系统可以结合本会话焦点定位任务；存在多个候选时需要澄清。

请求和工具写操作使用防重复机制，避免断网重试创建多份任务。保存日程前检查版本、时间冲突、可用时段、截止时间与工时覆盖。重新打开网页后，可以恢复已保存的历史与业务状态。

### 3.4 联网搜索与天气接口

网页搜索使用 Tavily 的基础搜索接口，返回标题、URL 和摘要。来源由实际工具结果生成，在页面独立展示并保存到历史；搜索失败时不能假称已经查证。索引摘要可能过时，搜索成功不等于已经获得最新事实。

天气查询使用 Open-Meteo：地理编码接口把城市转换为经纬度，天气接口返回气温、天气代码、体感温度、湿度、风速和今明两日预报。后端对字段、单位、数值、时间、响应大小与超时进行校验，再交给模型生成回复。回答注明来源及数据有效时间。

**Open-Meteo 数据是天气模型估计，不是校园现场传感器实测。** 免费接口适用于本项目的非商业教学用途；模型回复仍消耗千问额度。城市不明确、接口超时或数据不完整时，系统应说明原因，不编造气温。

### 3.5 网页与语音交互

页面提供对话、任务看板、日程、成员、项目切换、空闲时间及导出入口。回复支持标题、列表、加粗、代码和来源链接；对模型 Markdown 输出进行清理后渲染，避免直接显示大量排版标记或执行不可信脚本。

语音输入先转成可编辑文字，用户检查后手动发送，避免误识别直接执行任务。界面支持暂停、继续和停止输入，以及回复朗读和停止朗读。识别和朗读效果受浏览器、设备、网络和授权影响。

## 九、每位成员的心得

### 9.1 陈建志，3124007214

这次我对Agent的理解更具体了。接上模型只是第一步，还要让它在需要时选对工具，拿到结果再回答。像天气查询，能正常聊天不代表能查到天气，搜索到网页也不一定就有当前气温，需要把模型、工具和接口分开检查。

我觉得联调时最有用的还是看实际记录：调用了什么、返回了什么、页面最后显示什么。不能只用一句特意写好的指令测试，还得试“今天广州天气如何”这种平时会问的话，这样才容易发现使用中的问题。

### 9.2 陈信儒，3124004160

我比较关注任务状态有没有真正保存。页面上变成“已暂停”以后，刷新和导出也应该保持一致，否则用户就不知道哪个结果才是准的。任务标题、负责人和截止时间也要一起核对，不能只看状态变没变。

模型有时会传错参数，所以数据库和工具这一层的校验很重要。日程同样不能只排出一张好看的表，还要检查成员有没有空、时间是否冲突、任务能不能在截止前完成。把这些规则交给程序检查，比完全依赖模型回答更稳妥。

### 9.3 肖琳瀚，3124004184

谁在聊天、任务归谁，应该一眼就能看清。成员切换、任务筛选和任务转交看起来都和“人”有关，但作用不一样，提示不清楚就容易误操作。我觉得界面设计不只是把按钮摆好，还要让用户知道点下去会发生什么。

回复的排版和等待提示也很影响体验。满屏符号或者点发送后一直没有动静，都会让人以为程序出了问题。把列表、标题和来源显示清楚，再展示实际工具进度，比继续增加几个入口更能改善使用感受。

### 9.4 陈康泓，3124004159

多轮对话里的“它”看着只是一个字，系统却需要记住前面说的是哪项任务。切换成员或项目以后，上下文也不能混用。这让我觉得，记忆功能不只是把聊天文字存下来，还要保存当前操作对象，并在不确定时问清楚。

语音也是一样，能识别出文字只是开始，还要考虑暂停后文字会不会丢、什么时候结束、是否让用户检查后再发送。目前朗读可以播放，但手动停止还有问题。这类交互需要在真实设备和浏览器里试，单看代码或按钮存在还不够。

### 9.5 陈憬乐，3124004050

测试和报告都要把结果对清楚。一句“已完成”不够，还要看任务卡片、日程和导出文件是不是一致。如果中途报错后又成功了，也应该保留过程，不能只看最后一句回复就当作整轮没有问题。

整理演示材料时，我觉得截图最重要的是让别人看懂操作前后发生了什么。全屏图适合介绍界面，具体功能则用局部图更清楚。报告也要对应实际版本，把已验证的功能和还存在的问题分开写，比堆很多技术名词更有说服力。
